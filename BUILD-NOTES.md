# Onchain Wire — BUILD NOTES

First working version, scaffolded 23 Nov 2026 for the Pi Next Hackathon 2026
(registered team account: @findpump). Companion docs: `../PREP.md` (rules and
requirements) and `SUBMISSION-ASSETS.md` (portal copy, logo/preview notes).

## Run it locally

```bash
cd ~/workspace/pi-next/app
node make-feed.mjs        # (re)generate feed.json from the newest berita-x editions
node server.mjs           # serves on http://localhost:3141  (PORT env to change)
```

- In a desktop browser you get **demo mode**: full real news feed, Pi sign-in
  and payments disabled with an explanatory banner. This is deliberate — the
  app must stay reviewable outside Pi Browser.
- In **Pi Browser** (via the sandbox URL configured in the Developer Portal,
  sandbox.minepi.com) the same build runs the real Pi flow: Pi.init →
  Pi.authenticate → Pi.createPayment.
- Sandbox switch: `CONFIG.sandbox` at the top of `app.js`
  (`true` = sandbox/Testnet development, `false` = Mainnet production build).

## What is REAL vs STUBBED

| Piece | State | Notes |
|---|---|---|
| News feed (`feed.json`) | **REAL** | Generated by `make-feed.mjs` from the actual `~/workspace/berita-x/` editions (10 newest stories, real verified copy, sources, timestamps, categories). |
| Feed regeneration | **REAL** | `node make-feed.mjs [--limit N] [--dir PATH]` — run after each new edition publishes; handles both pipeline formats (`--- n/N ---` and `n/` thread splits). |
| Frontend reader (list, filters, article view) | **REAL** | Mobile-first, dependency-free, works in any browser. |
| Pi SDK load + `Pi.init` | **REAL** | `https://sdk.minepi.com/pi-sdk.js`, `version: "2.0"`, sandbox flag configurable. |
| Pi Authentication wiring | **REAL (client)** | `Pi.authenticate(['username','payments'], onIncompletePaymentFound)` on the sign-in button; shows the signed-in `@username`. |
| `POST /auth/verify` | **STUB** | Accepts the access token and returns the expected JSON shape, but does NOT call `GET https://api.minepi.com/v2/me` yet. Marked `TODO(prod)` in `server.mjs`. |
| Pi payment UI surface ("Support — 0.1 Pi TEST") | **REAL (client)** | Full `Pi.createPayment` call with all four callbacks wired to the backend endpoints. Clearly labelled TEST in the UI. |
| `POST /payments/approve` | **STUB** | Logs `paymentId`, returns `{ ok, stub, approved: true }`. Does NOT call the Pi Platform API. `TODO(prod)` marks the real `POST /v2/payments/<id>/approve` call. |
| `POST /payments/complete` | **STUB** | Logs `paymentId` + `txid`, returns `{ ok, stub, completed: true }`. `TODO(prod)` marks the real `POST /v2/payments/<id>/complete` call. |
| Static file server | **REAL** | Dependency-free Node `http`, path-traversal guard, `/healthz` endpoint. |
| Privacy policy | **REAL draft** | `privacy.html`, plain English; must be reachable at a public HTTPS URL for submission. |
| Logo | **PLACEHOLDER** | CSS "OW" mark only. Final PNG export still needed (see SUBMISSION-ASSETS.md). |
| Preview images | **NOT YET** | Capture list is written in SUBMISSION-ASSETS.md; screenshots must come from the real running app. |

No real Pi can move in this build: the Platform API is never called, and the
support payment is labelled TEST everywhere it appears.

## Remaining submission checklist

From `../PREP.md` (deadline: **Wed 6 Jan 2027, 14:59 WIB**; up to 3 apps;
only one team member submits each app; every team member must be registered
individually under the Hackathon tab):

1. **Public HTTPS hosting URL.** The portal requires the app (and the privacy
   policy) at public HTTPS URLs. See hosting section below. Localhost is only
   for development/sandbox.
2. **Developer Portal "New App" entry** (inside Pi Browser:
   pi://develop.pinet.com, or developers.minepi.com). ⚠️ At registration the
   app binds to **one network (Mainnet or Testnet) and the choice cannot be
   changed later** — decide deliberately before creating the entry. The app
   name chosen there determines the app URL.
3. **Server API Key.** After the app entry exists, copy its Server API Key
   from the app dashboard → set `PI_API_KEY` in the server environment →
   replace the three `TODO(prod)` stubs in `server.mjs` with the real
   Platform API calls (approve, complete, and `/me` verification; also
   verify amount/memo via `GET /v2/payments/<id>` before approving).
4. **PiNet integration.** Every submitted app must integrate PiNet: register
   and verify the app so it is reachable through its PiNet address
   (`<appname>.pinet.com` pattern) and loads correctly inside Pi Browser via
   that address; complete the portal's PiNet/validation checklist items.
   Test the full flow (sign-in + payment) through the PiNet URL, not only
   the raw hosting URL.
5. **Portal checklist assets.** Final logo PNG (trademark-safe — no Pi logo /
   π-dominant mark), English description (draft in SUBMISSION-ASSETS.md),
   preview screenshots from the real app, privacy policy URL (item 1).
6. **Production flags.** Set `CONFIG.sandbox = false` in `app.js` for the
   Mainnet build; remove the TEST wording from the support surface only
   when real payments are enabled.
7. **Feed freshness on the host.** Arrange for `make-feed.mjs` to run after
   each new berita-x edition (5×/day) or on a schedule, so the submitted
   app never shows stale news during judging.
8. **Demo video (mandatory).** ≤ 3 minutes, posted **publicly** (YouTube or
   similar), link goes in the submission form. Must cover: (a) what the app
   is and does, (b) feature/interface walkthrough, (c) who it is for,
   (d) the problem it addresses, (e) how Pi is part of the experience
   (Pi Sign-in / Pi payments). Record from the final version of the app.
9. **Optional midpoint submission** — details arrive by email after
   registration; selected apps get visibility + feedback before the final
   deadline. Worth taking if the app is ready early.

## Hosting options (public HTTPS)

| Option | Fit | Caveats |
|---|---|---|
| **Render (free web service)** | **Recommended for the submission build.** Native Node runtime — `node server.mjs` deploys unchanged; free HTTPS `*.onrender.com` URL; env vars for `PI_API_KEY`. | Free tier sleeps after inactivity (cold start ~30–60 s); acceptable for judging, or upgrade later. Feed regeneration needs a cron/wiring step (Render Cron Jobs or an external trigger). |
| **Nodaroo server "Museng"** (imam's free server, Pterodactyl panel, Sydney AU1, 2 GB RAM) | Already ours; zero extra accounts. Would need work: the panel egg is **Python-generic**, while this backend is Node. Options: port `server.mjs` to a small Python stdlib server (the endpoints are tiny), or test whether the panel's startup allows a bundled Node binary. | Free-panel allocations are typically raw IP:port over HTTP — **no TLS/domain**, and Pi requires a public **HTTPS** URL. Would need a Cloudflare Tunnel (or similar) in front to get HTTPS. Free-tier credit burn/persistence unknown — fine for a listener, riskier as the sole submission host. |
| **Cloudflare Tunnel (cloudflared)** | Free HTTPS hostname in front of any process we run (Nodaroo box, this VM while it lives, a home machine). Good fallback/complement to either option above. | Needs a Cloudflare account + a host that stays up; the tunnel target must run 24/7 during judging. |
| **Vercel / Netlify (static + serverless)** | Free HTTPS, great for the static frontend. | Backend endpoints would have to be rewritten as serverless functions (the single-file `server.mjs` model doesn't carry over directly). Extra work for no gain over Render for v1. |
| **Fly.io / Railway** | Real Node hosting with HTTPS. | Fly requires a credit card on file; Railway free credit is trial-like. Unnecessary while Render free works. |

**Recommendation:** deploy this exact build to **Render free tier** for the
submission (zero code changes, HTTPS included, `PI_API_KEY` as an env var),
and keep the Nodaroo server for what it was provisioned for (SSRF/webhook
listener duties). Revisit only if Render's cold starts annoy during judging.
